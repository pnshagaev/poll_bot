# Ручной pull бота в Proxmox VM 110

По результатам проверки ID 110 — виртуальная машина `services`, а не LXC.
Владелец подтвердил её использование и выбрал **ручной pull**. Имя этого документа
сохранено из исходной задачи. Таймера обновлений и SSH-деплоя из GitHub нет.

## Текущее окружение

- VM: `192.168.1.20`, Debian 13, Python 3.13, amd64.
- Proxmox: `192.168.1.10`; административный доступ сохранён.
- SSH с компьютера владельца: `ssh root@192.168.1.20`, по существующему ключу.
- Доступ через Console Proxmox также сохранён.
- Prowlarr, FlareSolverr, TorrServer и Transmission продолжают работать.
- Env заполнен владельцем; Telegram getMe проверен без отправки сообщений.
- По решению владельца `games.json` создан пустым; историю не переносим.

Для обновления VM сама обращается к публичному GitHub и PyPI по HTTPS.
GitHub-токен, WireGuard, проброс SSH с WAN и настройки keen-pbr для этого не нужны.
SSH доступен только для администрирования в разрешённой сети.
В GitHub Actions остаются тесты на push/PR в main и `workflow_dispatch`.
Actions не подключается к домашней сети и не запускает бот.

## Команды владельца

Из root-консоли **VM 110**, не из Shell хоста Proxmox:

```bash
# Узнать доступный и установленный commit. Без установки и restart.
basketball-bot-pull --check

# Получить main, проверить и установить версию.
basketball-bot-pull
```

С текущего компьютера можно выполнить те же команды напрямую:

```bash
ssh root@192.168.1.20 basketball-bot-pull --check
ssh root@192.168.1.20 basketball-bot-pull
```

Команда от root автоматически выполняет обновление от непривилегированного
пользователя `deploy`. Он может через sudo только restart, stop и reset-failed
`basketball.bot.service`. Production-процесс работает от `basketball-bot`.

Первый реальный запуск выполняет владелец после остановки прежней копии бота:
две одновременно работающие копии с одним токеном конфликтуют при long polling.
Подготовка команды и `--check` не являются разрешением запускать production.

## Что делает pull

1. Берёт локальную блокировку: второй pull одновременно не начнётся.
2. Получает текущий main по HTTPS в bare Git cache. Текущий код не меняется.
3. Извлекает только код, requirements и тесты. Tracked `.env` и `games.json`
   не извлекаются и не загружаются приложением.
4. Создаёт временный Python 3.13 venv, устанавливает зависимости без компиляторов
   и запускает полный pytest на VM. Проверяет поддержку внешнего пути JSON.
5. Фиксирует проверенные версии зависимостей и скачивает их wheels.
6. Проверяет, что main не изменился во время подготовки. Затем собирает архив
   с SHA коммита и checksum; скачанная версия не устанавливается при ошибке тестов.
7. Устанавливает отдельный release venv из проверенных wheels без сети, атомарно
   переключает current, перезапускает сервис и наблюдает стабильный PID 30 секунд.

GitHub Actions проверяет код независимо. Ручной pull повторяет тесты с реально
устанавливаемыми версиями зависимостей на целевой Debian, поэтому установка не
зависит от доступности или срока хранения GitHub Actions artifacts.
Повторный pull уже установленного активного SHA не перезапускает бот.

## Каталоги и данные

```text
/opt/basketball-bot/
  source.git/                         # bare cache публичного репозитория
  releases/<commit-SHA>/              # код, constraints, wheels, venv
  current -> releases/<active-SHA>
  previous -> releases/<previous-SHA>
  incoming/                          # временные архивы
/usr/local/bin/basketball-bot-pull     # установленная ручная команда
/usr/local/lib/basketball-bot/deploy-release
/var/lib/basketball-bot/games.json     # постоянные изменяемые данные
/etc/basketball-bot.env                # root:root, 0600; вне Git
```

Файл env редактируется только владельцем: `nano /etc/basketball-bot.env`.
Его значения команда pull не читает, не выводит и не перезаписывает.
Unit читает env через systemd; задаёт `GAMES_FILE=/var/lib/basketball-bot/games.json`
и `PYTHON_DOTENV_DISABLED=1`. Без GAMES_FILE приложение сохраняет старый путь
рядом со скриптом для совместимости прежней установки.
JSON сохраняется атомарно, поэтому ссылка на сам games.json не используется.

После успешного обновления сохраняется максимум пять релизов; current и previous
защищены от удаления. После неудачи кандидат может остаться для диагностики до
следующего успешного обновления. Git cache не используется как runtime checkout.

## Первый запуск и проверка

1. Опубликовать эти изменения в main и дождаться успешной проверки GitHub Actions.
2. Выполнить `basketball-bot-pull --check` в VM.
3. Владелец останавливает старого бота на прежнем сервере.
4. Владелец выполняет `basketball-bot-pull` в VM и дожидается окончания.
5. Проверить в VM:

   ```bash
   systemctl is-active basketball.bot
   systemctl show basketball.bot -p MainPID -p NRestarts
   readlink -f /opt/basketball-bot/current
   journalctl -u basketball.bot -n 60 --no-pager
   ```

6. Проверить `/ping`, `/games`, `/schedule` в Telegram. `/test` создаёт реальные
   опросы, поэтому для обычной проверки не нужен.
7. После успешного запуска при необходимости включить автозапуск **самого бота**:

   ```bash
   systemctl enable basketball.bot
   systemctl enable --now basketball-bot-healthcheck.timer
   ```

Healthcheck timer только следит за процессом и не обновляет код.
Он проверяет состояние ежечасно и включён в действующей VM. При падении срабатывает
также OnFailure. Уведомления содержат состояние, код завершения и очищенный текст
исключения; приложение сообщает тип и текст ошибок обработчиков и отправки опросов.
Передача полного traceback и секретов в Telegram запрещена.
До первого запуска бот и этот timer остаются выключены.
Не оставляйте автозапуск старой копии на прежнем сервере после cutover.

## Откат

Если новый процесс остановился или автоматически перезапустился за контрольные
30 секунд, восстановится прежняя ссылка current, сервис перезапустится и будет
проверен повторно. Команда завершится с ошибкой даже при успешном восстановлении.
При неудачном первом запуске без предыдущей версии сервис останавливается.

Ручной откат из root-консоли VM:

```bash
runuser -u deploy -- /usr/local/lib/basketball-bot/deploy-release --rollback
```

JSON и env при откате не заменяются. Миграций БД в проекте нет; будущие несовместимые
изменения JSON потребуют отдельной процедуры. Устаревший либо расходящийся SHA не
установится поверх потомка: deploy-release проверяет историю под локальной блокировкой.

## Подготовка новой VM или обновление служебных скриптов

Администратор внутри гостевой Debian 13 устанавливает `git`, `python3-venv`,
`openssh-server`, `sudo`, `ca-certificates`, `curl`. Не запускайте prepare-target на Proxmox.
Из проверенной копии этого репозитория, внутри VM, от root:

```bash
bash deploy/prepare-target.sh
```

Скрипт создаёт пользователей и каталоги, устанавливает unit, мониторинг, pull и
deploy-release, узкий sudoers; проверяет SSH-конфигурацию и не запускает бот.
Существующие authorized_keys не удаляются. При желании можно передать единственный
аргумент — дополнительный публичный Ed25519-ключ для SSH-пользователя deploy.
Конфигурация уже работающего бота автоматически не заменяется: сначала требуется
отдельное окно обслуживания. Команда pull не обновляет root-owned units и скрипты.

## Диагностика

- Ошибка Git/PyPI: проверить HTTPS/DNS из VM; действующий бот до активации не трогается.
- Ошибка тестов: текущий релиз не меняется, исправить код в main и повторить pull.
- main изменился: дождаться проверок нового коммита и повторить команду.
- Процесс падает: просмотреть journal локально, проверить env, права JSON и отсутствие
  второй polling-копии. Журнал не публикуйте: он может содержать приватные данные.
- Нет места: проверить `df -h`, релизы и pip cache пользователя deploy.
- Внезапная потеря питания или SIGKILL могут помешать trap; перед повтором проверить
  current и состояние сервиса. Не удалять активный/предыдущий релиз вручную.

Роутер, VPN LXC, keen-pbr и Proxmox-конфигурация для ручного pull не изменялись.
Проверка стабильного процесса ограничена 30 секундами; доставку опросов она не доказывает.
